# 正式发布、后台更新与版本回退

## 当前范围

后台入口为 **系统 → 系统更新**（`/admin/updates`）。打开页面自动检查稳定版，普通检查缓存30分钟，手动检查最短间隔15秒。失败、限流、尚无发行版、公钥未配置都会明确显示，不会把错误当成“已经最新”。只允许管理员访问。

Docker使用签名清单中固定的GHCR镜像摘要，不跟随可变的 `latest` 标签。原生Linux/Termux使用相同签名清单中的源码包和SHA256，在独立版本目录构建后切换。只更新程序，保留原端口、域名与持久数据目录。

`v1.0.1` 已通过签名发布流水线正式发行，GitHub Release 包含源码包、发行清单和签名。主分支源码仍标记为 `1.0.1 / development`；同版本开发版可检查到 `1.0.1 / stable`。正式发行不等于在每台主机启用了更新代理；未启用时只能检查版本，不能从后台执行升级。

本版自动更新适用：通过大彪TV独立脚本管理、已经完成首次安装、健康的 **SQLite** 部署。手动旧部署需要先在备份后对接管理目录，不能重新安装覆盖旧站。MySQL/PostgreSQL自动更新暂时拒绝执行，需建立外部数据库备份和迁移流程；检查版本仍可用。

macOS 上以 Vite `127.0.0.1:5173` 运行的开发站不是受支持的托管安装。它可以检查正式版，但现有独立更新代理要求 Linux root/systemd 或 Termux 服务管理器；不要为了显示更新按钮而伪造代理状态或直接让网页启动高权限更新进程。

使用私有 `data/live-tv.json` 的站点在升级前还须单独备份并核对该文件：`v1.0.1` 的自动备份流程尚未将直播 JSON 纳入快照。程序切换通常保留持久数据目录，但不能把这当成完整备份或自动回退保障。

## 信任与权限

- 发行来源固定为 `dabiao996/dbtv` 的正式Release，拒绝草稿、预发行、任意URL和任意镜像仓库。
- `release-manifest.json` 使用Ed25519签名，包含版本、提交、源码SHA256、镜像digest及保守的数据兼容标识。
- 私钥只由发布者离线保存/GitHub Actions Secret持有，**不在网站、镜像、源码、更新队列或运行日志里**。
- 公钥 `deploy/update-public.pem` 随源码发布；主机启用时将其固定到root持有的私有策略文件。应用更新不能自行更换主机信任根。
- 网页不挂载Docker socket、不以root执行更新、不接收shell命令；只提交固定动作和版本/历史记录ID。管理员操作还需同源请求、再次验证密码及二次确认，尝试次数有限制。
- 主机独立代理再次验证签名、版本、目标镜像/源码和历史记录，使用独立操作锁，拒绝并发、过期或含额外参数的请求。管理代码复制到独立私有 `manager/`，不从网页可写目录执行root代码。
- 更新失败或断电留下未完成标记时，不自动抢锁/继续迁移；管理员需核实进程、记录和备份。不要随意删除 `operation.lock`、`updates/active.json` 或安装锁。

## 发布者：首次配置

由仓库拥有者在自己的安全电脑执行，私钥路径必须在项目外，不能发到聊天：

```sh
node scripts/release-keys.mjs /你的安全目录/dbtv-release-private.pem deploy/update-public.pem
```

仅提交公钥；将**私钥文件内容**通过GitHub设置页面保存到仓库Actions Secret：`RELEASE_SIGNING_KEY`。脚本拒绝覆盖现有密钥，也拒绝把私钥写入项目。自行备份私钥，丢失后需要人工更换所有部署的信任根，不提供静默换钥。

正式发行前：

1. 首版为 `1.0.0`。后续将 `package.json`、`package-lock.json` 和 `release.json` 版本改成一致的新版本，例如 `1.0.1`。可用 `npm version 1.0.1 --no-git-tag-version` 修改前两个，再编辑 `release.json`；主分支channel保留development。
2. 提交并推送经过测试的代码和公钥。创建并推送对应标签（首版 `v1.0.0`，之后如 `v1.0.1`），触发 `.github/workflows/release.yml`。本地改代码不会自动推送或发布。
3. 工作流校验版本与密钥，运行lint/build/测试，打包不含私有数据和依赖的源码包，构建amd64/arm64镜像到 `ghcr.io/dabiao996/dbtv:对应版本号`，签名精确digest与源码校验值；最后上传全部资产，再发布正式Release。
4. 首次GHCR包可能是私有的，请在GitHub Packages确认包对目标用户公开可拉取；首版公开更新不把仓库Token发给网站用户。GHCR不可达/权限不足会停止更新而不关闭原站。

工作流不会覆盖已发布的正式Release。失败时可以检查并重试未发布草稿；发布内容应不可变，修正错误请升版本。建议在GitHub启用发行不可变保护。工作流已固定第三方Action的提交SHA；之后升级Action也应审阅。

## 部署者：启用后台更新

须使用包含本功能和公钥的管理源码，先确认当前网站及数据库正常。Linux示例：

```sh
sudo /opt/dabiao-tv/tools/node/bin/node /opt/dabiao-tv/app/scripts/tv.mjs enable-updates --home /opt/dabiao-tv
```

该操作确认后创建root持有的独立管理副本和systemd更新队列timer。Termux在宿主用 `node` 执行同一命令（目录改为Termux管理目录），使用单独 `termux-services` 服务，不要求root；其安全边界仍是同一Android应用用户，不能假装具有Linux root隔离。

服务不会自行决定升级，只在管理员确认请求后工作。回到网站后台检查版本、阅读说明、勾选风险确认、验证管理员密码，点击“备份并更新”。重启期间页面可能短暂断开，恢复后自动重新连接并展示结果。

也可在主机执行：

```sh
sudo node scripts/tv.mjs check-update --home /opt/dabiao-tv
sudo node scripts/tv.mjs update --home /opt/dabiao-tv --version 1.0.1
sudo node scripts/tv.mjs update-history --home /opt/dabiao-tv
sudo node scripts/tv.mjs rollback --home /opt/dabiao-tv --record 上述记录ID
```

无全局Node时替换成安装目录中的私有Node路径。更新和回退都需启用信任策略；命令不接受任意下载地址、镜像名称或恢复文件路径。未来总工具箱可以直接调用这些命令。

## 更新及回退顺序

1. 当前站点必须已安装且健康，先下载并校验新镜像，或在独立目录下载、校验和编译源码；准备失败不关闭当前网站。
2. 停止站点，确认停止成功，再用旧程序创建SQLite一致性快照，并备份私有连接配置、安装锁及部署配置。Docker用旧本地镜像启动一次性离线备份进程，不把停止的容器当成还能执行命令。
3. 备份要求唯一有效SQLite快照，且配置复制不跟随软/硬链接；只有全部成功才写 `backup.json: complete:true`。主机最终备份目录由管理用户持有，网页不能篡改。
4. 先保存旧程序/镜像和备份记录，再切换。端口、域名和数据目录不变。健康检查同时检查实际响应版本、网站和数据库，不仅检查进程是否存在。
5. 成功后才标记完成。当前保留程序/镜像与备份，不执行全局Docker清理，也不删除别人的镜像、数据卷或备份。

**程序回退不等于数据库恢复。** 数据兼容标识保守地包含Prisma结构、后端和迁移相关脚本。完全一致时允许程序自动恢复/回退，不回写旧数据库；不一致或无法判断时，新版一旦启动过就不自动降级。失败会停止程序、保留备份并提示人工处理。

后台历史只展示可验证记录；旧镜像/旧构建被手动删掉后也拒绝回退。回退本身再次停站和备份当前数据库，以便排查。跨结构版本要由管理员评估迁移和备份后人工恢复；恢复旧快照可能丢失之后新增的账号、积分和观看记录，不能一键默默执行。

## 文件与验收

主机 `update-policy.json`、`manager/`、`updates/` 是管理私有文件；`data/updates/` 仅为受限队列和不含密码/备份路径的状态。备份和运行版本不属于待上传GitHub的源码。

自动测试使用临时目录、临时Ed25519密钥和隔离模拟，覆盖签名篡改、版本比较、权限/同源/密码验证、备份失败、健康失败、兼容回退、不兼容锁定、队列校验及持久记录。`v1.0.1` 已完成 GitHub 签名发布，仍未完成真实 Docker/Linux/Termux 的端到端升级验收；请先在隔离测试设备验证，再用于生产。
